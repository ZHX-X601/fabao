# 2026-09-13

## 【已修】FastGPT chatId 硬编码导致跨用户/跨对话记忆串台

**现象**：zhang 聊过"张三欠5000"，新对话仍能复述；新注册 lisi 账号也照样"记得"，且 FastGPT 后台所有对话挤在同一条日志里按时间追加（消息总数 44）。

**根因**：`ai_service.py` 第 80 行 `payload = {"chatId": "fabao-backend"}` —— chatId 是**写死的常量**，与前端的 conversation.id / user_id 完全无关。
FastGPT 官方语义：`chatId` = 会话主键 + 记忆开关 + 落库开关。传了就会「自动从库取该 chatId 的历史」并落库；后台"对话日志"一行 = 一个 chatId。所以所有用户所有对话共用一条记忆，全量历史被喂给模型。
次因：后端自己还传了最近 10 条 messages（MAX_HISTORY=10），与 FastGPT 侧记忆叠加成双重历史。
FastGPT 后台"使用者=Owner"是正常现象——API Key 属于应用 owner，OpenAPI 方式无法识别真实用户。

**修复方向**（用户要求先不改）：
- `ai_service.generate_reply()` 增加 conversation_id/user_id 参数，chatId 改为 `fabao-chat-u{user_id}-c{conversation_id}`（或 `fabao-chat-c{conversation_id}`，id 自增全局唯一）；长度需 < 250
- `document_service.py` 的 `fabao-doc-{doc_type}`、`contract_service.py` 的 `fabao-contract-review` 同为写死 chatId，单次任务建议用 uuid4 或直接不传 chatId（不传=无记忆不落库）
- 修复后 FastGPT 后台旧的 `fabao-backend` 记录需手动删除
- 前端删对话时后端只删本地，FastGPT 侧 chat 记录会残留（无害，chatId 唯一后不会再被写入）

**已实施（同日）**：chatId 命名统一为「模块前缀 + u{user_id} + 表主键」，三表主键不会撞号：
- 对话：`fabao-chat-u{uid}-c{conversation_id}`（chat.py 拼好传给 ai_service.generate_reply 新增的 chat_id 参数）
- 文书：`fabao-doc-u{uid}-d{document_id}`；document.py 流程改为「先建记录（generated_content 置空落库拿主键）→ 生成 → 回填 content」，因为原流程生成时还没有主键
- 审查：`fabao-review-u{uid}-r{contract_id}`（合同先上传后审查，主键天然存在；同一合同重新审查共用 chatId，历史互相关联）
- generate_document/review_contract 签名均加 user_id + 记录主键参数；后端导入验证通过

## 历史记录响应登录状态变化

## 重构文书生成 docx 输出（解决"民事起诉状排版混乱"问题）

**问题根因**：`backend/app/api/document.py` 的 `download_document` 接口只用一行行写入 + 简陋的"标题加粗判断"（`len <= 12 and no 冒号 and no 逗号`），导致字体/字号/对齐/缩进完全错乱——用户原起诉状所有段落 font=None、size=None、bold=None。

**解决方案**：新建专业 docx 生成服务 `backend/app/services/document_docx_service.py`，参照 `report_service.py` 的字体策略：
- 必须同时设置 ascii + eastAsia（否则中文变方块）
- 字体：Times New Roman (ascii) + Microsoft YaHei (eastAsia)
- 按文书类型提供专业排版（标题 22pt 居中加粗、节标题 15pt 加粗、正文 12pt 首行缩进 2 字符 1.6 倍行距、落款右对齐）

**4 种文书的版式**：
- 民事起诉状：标题 → 原被告 → 诉讼请求（中文编号）→ 事实与理由 → 证据清单 → 此致 → 落款
- 民事答辩状：标题 → 答辩人/被答辩人 → 答辩意见 → 事实与理由 → 答辩结论 → 此致 → 落款
- 律师函：标题（居中加大间距）→ 致（14pt 加粗深蓝）→ 引言 → 事实陈述 → 法律意见 → 郑重函告 → 履行期限 → 落款
- 授权委托书：标题 → 委托人/受委托人 → 引言 → 委托事项 → 代理权限（智能识别"一般/特别授权"）→ 委托期限 → 落款

**接口改造**（第二轮修正）：`DownloadRequest` 最终改为 `{content, doc_type, form_data?}`。优先用 `content`（AI 生成的文书全文）走 `format_ai_content_docx` 智能排版，无 content 时降级到 `form_data` 模板拼接。前端 `handleDownload` 传 `{content: resultText.value, doc_type}`。

**第二轮修正原因**：第一轮把 `DownloadRequest` 改成只接收 form_data，等于把 AI 生成的内容全丢了——下载的 docx 变成了"前端输入的表单值模板拼接"，用户吐槽"把前端输入的文字打出来干嘛"。正确做法是保留 AI 生成内容，后端对其做智能排版。

**第三轮改造：纯文本 → 结构化 JSON 返回**：
- 核心思路：合同审查之所以排版好，是因为返回 JSON 可精确控制；文书生成原来返回纯文本靠正则猜排版，不可靠
- 设计通用文书 JSON schema：`{"title": str, "sections": [{type, ...}, ...]}`
- section type 8 种：party(当事人)、heading(节标题)、numbered(编号项)、paragraph(正文)、center(居中)、signature(落款)、blank(空行)、notice(提示)
- 每种 type 对应确定性的 Word 样式，无需正则猜测
- 降级模板也生成 JSON 格式（与 AI 返回格式统一）
- AI 返回的 JSON 可能被 ```json``` 包裹或前后附带文字，`_extract_json` 做三层解析
- `_validate_sections` 校验并修正无效 section（未知 type 降级为 paragraph）
- 占位符用长度区分：人名6、身份证18、电话11、日期8、金额10、地址20、法院律所16

**验证**：4 种文书 POST /documents/download 都返回 200，37KB 左右；解析 docx XML 确认：标题 22pt CENTER 微软雅黑、当事人 12pt 加粗 indent=24pt、节标题 15pt 加粗。

## 替换"百分比进度条"为"阶段骨架提示"

**问题根因**：DocGenerate 和 ContractReview 都用 `setInterval` 每 120-180ms 随机 +6~+17 模拟进度 → 1-1.5 秒就到 100% → 然后真实 API 还在等 → 用户以为卡了。`el-progress` 进度条无法预估等待时间，本身就是 bad UX。

**解决方案**：彻底放弃百分比进度条，改用「阶段清单 + 当前激活项旋转图标 + 待办项灰显」的骨架提示：
- **DocGenerate** 4 阶段：理解信息 → 检索法规 → 构建框架 → 生成全文
- **ContractReview** 5 阶段：解析文本 → 识别条款 → 比对规则 → 评估等级 → 生成报告
- 阶段推进：每 2-2.5 秒切下一项（4-5 项共 8-12.5 秒，覆盖大多数 5-15s 等待窗口）
- 后端 API 一旦返回立即跳到结果页（不卡阶段动画）
- 视觉：旋转圆环 + 文档图标 + 阶段清单（已完成绿色对勾 / 进行中金色旋转 / 待办灰色小圆点）

**关键技术点**：
- `currentStageIdx` ref 跟踪当前阶段
- `stageTimer` 每 2-2.5s 推进一步
- `clearTimers()` 统一清理（onBeforeUnmount + restart + resetAll）
- `el-icon Loading` + CSS `@keyframes spin` 旋转动画
- `Loading` 图标需要从 `@element-plus/icons-vue` 单独 import
